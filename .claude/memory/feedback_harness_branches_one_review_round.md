description: On a branch that only edits the harness (agent prompts in .claude/commands, scripts/chain*.sh, hooks, workflow docs), run one read-only review round, fix confirmed behaviour differences only, and hand the diff to Frank to read — do not run /verify's four rounds, and do not let the timer build it.
type: feedback
---

On a branch whose diff is only the harness — agent prompts under `.claude/commands/`, `scripts/chain.sh` / `scripts/chain-next.sh`, `.claude/hooks/`, the workflow docs — do **not** run `/verify`'s multi-round loop. Run the suite once, run **one** read-only reviewer round with a checkable question, fix only confirmed behaviour differences, list everything else unfixed, and give Frank the diff to read. Say in the pull request that it had one review round and a human read; do not report it `VERIFIED`, because the full procedure was not run. Build such an issue by hand in a session Frank is watching, and leave it without the `ready` label (or `parked`) so the timer does not pick it up.

**Why:** Frank's standing instruction, 2026-10-09 ("careful with the use of verify when it comes to the harness — I'm tempted we should not do the same rounds here", then "standing rule for harness-only branches, save it"). The evidence was #346: the unattended chain ran four rounds on a `verify.md` edit, each round found Important problems in the round before, and round four failed it — the prompt was being edited by the loop it describes. The loop converges on code because a fix can be checked against a test; a fix to prose is new prose with nothing objective to check it against, so every round finds something in the last. #328 and #331 parked the same way. My interpretation: the rule is about branches where *every* changed file is harness; a branch that changes `src/` as well still gets the normal `/verify`.

**How to apply:** check `git diff --name-only main...HEAD` first. If it is harness-only, brief the single round's reviewers with a question that has a right answer (for a restatement: "does any cell differ from what `main` says today?") and ask them to list problems `main` already had separately, so they are not fixed in passing. Where the work is a restructure plus behaviour changes, split it: land the restructure alone as a no-behaviour-change restatement, then make each behaviour change as a small edit — #346 was split into #356 for this reason.
