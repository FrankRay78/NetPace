description: docs/ updates must describe only what exists today; no sections about unimplemented features tracked by GitHub issues, even when a /speckit.tasks plan mandates them
type: feedback
---

When editing the canonical docs under `docs/` (e.g. `docs/RELEASING.md`, `docs/architecture/*`, `docs/conventions/*`), describe **only** what the current codebase does. Do **not** add sections about future features tracked by GitHub issues — even when a `/speckit.tasks` plan mandates them.

Examples of forward references that are NOT acceptable: a "Future X Pipeline" section describing a release target no runner has produced yet; calling-side guidance about an abstraction that hasn't been introduced; references to a component that's still hypothetical or only exists as an open issue.

**Why:** Forward-referenced docs rot until the referenced feature actually lands. They mislead readers about current behaviour, create maintenance debt, and trigger confusing edits when the eventual implementation diverges from the speculative description. Task plans generated by `/speckit.tasks` will sometimes ask for doc sections that describe outcomes of *other* unmerged features — push back rather than write them.

**How to apply:** If a task plan asks you to write about something that's only an issue today (no code, no tests, no merged spec for it), push back **before** implementing the doc edit. Propose either (a) deferring the doc work until the feature actually ships, or (b) rewording the section to describe only the current state (which often means "drop the section entirely"). Live spec references (e.g. `specs/<NNN>-…/contracts/…`) are fine *while the spec is merged in this repo*; open GitHub issue numbers for unimplemented features are not — and see [feedback_no_spec_references.md](feedback_no_spec_references.md) for why even spec links shouldn't leak into durable surfaces.
