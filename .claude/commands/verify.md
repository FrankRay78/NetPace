---
description: Orchestrator that turns "implementation looks done" into a reviewed, test-green branch — runs the full suite first and hard-gates on it, then reviews in up to four rounds, fixing the confirmed findings its rules table calls for and committing each round, with a last round that only reads. Stops short of the pull request. Runs unattended, so it can drive a loop.
---

Read `CLAUDE.md` for project context before proceeding.

`/verify` is the stage between `/build` and `/raise-pr`: it turns a feature branch into a **formatted, test-green, reviewed, fully-committed** branch with a clean working tree. It does not push, open a PR, or merge — `/raise-pr` owns all of that, and you run it yourself afterwards.

`/verify` composes NetPace's existing commands behind one hard gate: **the full test suite gates everything downstream, and no review happens unless it is green.** The gate is structural — the review step is downstream of the step-1 exit code, so it cannot begin against un-verified or red code. Do not add a hook to police this ordering; the exit code *is* the gate. The one step that precedes the suite is formatting (step 1a), which is cosmetic and is itself covered by the gate that follows it.

**The review is a loop, not a single pass.** A fix written in response to a review is new code, written quickly against a reviewer's framing of the problem, and it often changes error handling — the riskiest code on the branch, and historically the only code on it that nothing but the suite ever read. So steps 2 and 3 repeat: each round reviews what the previous round committed, until a round finds nothing to change.

**The last permitted round only reads.** The loop runs at most four rounds. Rounds one to three may fix; if the third round still made a fix, a fourth and last round reviews that fix and changes nothing, and what its reviewers report is what decides the verdict. So every fix `/verify` commits has been read by a reviewer by the time the loop reaches a verdict, whichever verdict that is — a `VERIFIED` branch contains no change that some reviewer who did not write it has not read, and a `FAILED` one names the problem a reviewer actually found rather than failing over an unread fix because the bound ran out.

`/verify` is designed to run to completion **without prompting**, so it can be driven by an automated loop (e.g. verifying many features back-to-back) as well as invoked directly. Reflection (`/capture-learnings`) is deliberately **not** a step: it needs human curation and batches better across many features, so it belongs at a supervised checkpoint after a batch — not inside each verify, where it would either block the loop or be auto-skipped to nothing.

Raising the pull request is deliberately **not** a step either. It is the one irreversible, outward-facing act in the chain: everything `/verify` does is safe to re-run, and pushing a branch and opening a PR is not. Keeping it a separate deliberate `/raise-pr` invocation is what makes the rest of the chain freely repeatable.

**Stop-on-failure is global:** if any step fails — the tree is dirty, a suite run is not green, the format tool errors, a review subagent errors, the last round finds a material problem — STOP at that step, report it to the invoker, and do not run any later step. Two things belong in *every* such report once the loop has begun: the state of the working tree, and — **only where the latest commit is a fix commit that no reviewer read** — that commit named as a change no reviewer has read. Check before asserting it, because the stops differ, and because the ordinary paths no longer produce one: the last round reads the third round's fix before any verdict, so a run that ends at the bound leaves nothing unread. What can still leave an unread commit is a stop *mid-loop* — a reviewer erroring in round two leaves round one's commit genuinely unread, and so does a `/verify` killed at its time limit. By contrast a red re-run in round three leaves every committed round already read and the *tree* dirty with the failed fix. The qualifier matters at the other end too: if a reviewer errors in round one, the latest commit is step 1a's format commit or whatever `/build` left, and naming that as an escape from the review loop would be misleading — round one's own diff covers it. Reporting a reviewed commit as unread is its own failure — it sends a human to re-read code two rounds already cleared, and makes the rest of the report less believable.

## Steps

**Every STOP below ends its report with the verdict line, and nothing after it.** Where a step names the reason (`FAILED reason=dotnet format failed`), report that reason verbatim; where it does not, write a short reason of your own. Whatever else the stop has to say — which finding was raised and by whom, what state the tree is in, what the recovery is — goes *above* that line, however naturally it reads to close on it. This is stated once here because it governs all of them: a stop message whose last line is not the verdict reaches `scripts/chain.sh` as the far less useful `no readable verdict` instead of the reason, and `scripts/chain-next.sh` then parks the issue with that non-reason — losing a two-hour stage's diagnosis to a formatting slip.

0. **Preconditions (before any suite run or review).** Each of the three is a **failure**, so each STOPS with the *Final report*'s `FAILED reason=` verdict line as the report's last line and nothing after it. Report the reason below verbatim; the explanatory sentence for a human goes *above* the verdict line.
   - Run `git rev-parse --abbrev-ref HEAD`. If it is `main`, STOP immediately with `FAILED reason=/verify was run on main, not a feature branch`. Do not run the format pass or the suite, do not spawn reviewers.
   - Run `git log main..HEAD --oneline`. If empty, STOP immediately with `FAILED reason=no commits on this branch over main`. Do not run the suite or spawn reviewers.
   - Require a **clean working tree**. Run `git status --porcelain`; if it is non-empty, STOP with `FAILED reason=the working tree has uncommitted changes`, adding that committing or stashing them is the recovery. A clean tree is what makes step 3 simple and correct: after the review, *anything* that shows up in the tree is a review edit and nothing else, so there is no need to separate review edits from pre-existing local changes.

   The first two checks run up front purely on cost grounds: a full format, a full suite run and a full review are minutes of work, and on `main` or an empty branch every one of those minutes is spent to reach a conclusion a cheap `git` call already had. The clean-tree check earns its place differently — it is the invariant that makes step 3 correct, as described above.

1. **Format (1a), then the full test run (1b).**

   **1a — Format the tree.** Run:

   ```bash
   dotnet format ./src/NetPace.sln
   ```

   **This is the bare command, deliberately — the same one CI runs** as `dotnet format ./src/NetPace.sln --verify-no-changes` ([dotnet.yml](../../.github/workflows/dotnet.yml)). It was previously the narrower `dotnet format style … && dotnet format whitespace …`, which can leave a tree that CI's check then rejects: a branch verified here would fail the format check on the pull request. Use CI's command, so what passes here is what passes there, whatever the gap between them turns out to be. The bare command also runs analyzer fixes, so read what it changed rather than assuming it only moved whitespace.

   The explicit `./src/NetPace.sln` argument is **required, not decorative**: `dotnet format` looks for a project or solution in the *current directory only*, and NetPace's solution is at `src/`, not the repo root. Omitting it fails with `Could not find a MSBuild project file or solution file`.

   - Formatting runs **once here, and once more inside each round that applies edits** (step 3) — never per commit. It is cosmetic work at a cadence that already costs minutes — see *Formatting is not verification* in [agentic-workflow.md](../../docs/agentic-workflow.md). This pass exists to bring the branch as `/build` left it into line; step 3's exists because a review fix written after this pass would otherwise reach the pull request unformatted.
   - **If formatting changed files, commit them now** — `git add -A` and a message in the same `Refs #<N>: <imperative>` form step 3 uses, e.g. `Refs #328: apply dotnet format` — *before* running the suite. This restores the clean working tree step 0 established, which is what keeps step 3's "anything in the tree is a review edit" invariant true. Do not carry format edits forward into the review commit; they are a separate concern and belong in their own commit.
   - **If formatting changed nothing, make no commit.** A branch already in format reaches step 2 with the commits `/build` left and no extra round to review a format commit that does not exist.
   - A **non-zero exit** from `dotnet format` is a real failure (bad workspace argument, unparseable source) ⇒ **STOP and report** with `FAILED reason=dotnet format failed`. A clean run that merely rewrote files is not a failure — that is the tool doing its job, and the distinction is the exit code, not whether `git status` is dirty afterwards.
   - Formatting deliberately precedes 1b so that any change it makes is verified by the suite below, rather than landing after the gate has already passed.

   **1b — Full test run (always).** Run `dotnet build ./src && dotnet test ./src` — always, including docs-only branches. Do not add a skip path for docs-only branches: the suite is fast, and this is the first whole-suite gate after `/build`, whose run precedes formatting and review fixes. The `gh pr create` `PreToolUse` hook re-runs the suite, but that hook fires inside a separately invoked `/raise-pr` that may not happen for a long while, or at all — so skipping here would leave a branch reported verified that no suite ever ran against.
   - Gate on the run's **exit code**, not on any stored marker.
   - **Not green ⇒ STOP:** report the failures to the invoker and do nothing else — no review subagents.
   - **Green ⇒ continue.**

2. **Review round (synchronous — this is Review A).** Steps 2 and 3 are a loop: a round reviews a diff, the loop applies and commits what that review warrants, and the next round reviews what the last one committed. **The round bound is four rounds in total, round one included** — nothing in `/verify` reviews beyond that, and that fixed bound is what makes the loop terminate. Round one is the review `/verify` has always run; a branch that needed a fix needs a second round to read that fix; a third absorbs one bad fix.

   **Rounds one to three may fix. Round four — the last the bound allows — only reads.** It is reached only when round three applied edits, and it exists to read that third fix. It runs the same reviewer set, over the same kind of diff, briefed identically; the only difference is what the loop does with its findings, which is the round-four column of the table below. **Make no edit to the working tree in round four**, however cheap or clearly correct a finding looks: its findings are the verdict, not a work list, and an edit made there would be a fourth fix that no round could read. Before it decides anything, confirm the round number — a round-four fix is the one mistake this design cannot absorb.

   **What this round reviews.**
   - **Round one** — the whole branch diff, `git diff main...HEAD`.
   - **Every round** — note `git rev-parse HEAD` before spawning anyone. Step 3 opens by checking it.
   - **A follow-up round** — only what the previous round committed, `git diff <that round's base>..HEAD`, where *the round's base* is the commit HEAD pointed at before step 3 committed that round's edits. Step 3 records it, so a follow-up round reviews an exact diff rather than guessing at one from the log.
   - **An empty follow-up range is a bookkeeping failure, not a clean round.** Check the range is non-empty before briefing anyone; if it is empty, the base is wrong — most likely taken after step 3's commit instead of before it — and the reviewers would be handed nothing, truthfully report nothing, and leave the previous round's commit read by no one while the run reported `VERIFIED`. That is the exact failure this loop exists to prevent, so **STOP and report** rather than treating a review of zero lines as a clean round.

   **Who reviews.**
   - **Round one — the full applicable set, in two waves**, exactly as below.
   - **A follow-up round — a narrower set over the fix diff only, in a single parallel wave:** `pr-review-toolkit:code-reviewer` and `pr-review-toolkit:silent-failure-hunter` always, plus three conditional on what the round actually touched — `pr-review-toolkit:pr-test-analyzer` for a test file, `pr-review-toolkit:comment-analyzer` for a comment or a documentation file, and `pr-review-toolkit:type-design-analyzer` for a new or changed type. Decide all three off the round's own `git diff <base>..HEAD` rather than from memory of what you edited: the file list settles the documentation case, but a comment or a type can change inside a file whose name says nothing, so read the diff content and not just `--name-only`.
   - **Only `pr-review-toolkit:code-simplifier` and `/review-slop` are excluded outright**, as against the three above whose conditions may simply not be met. `code-simplifier` is excluded structurally: it is the one reviewer that edits files, so leaving it out is what means there is **no wave 2 in a follow-up round** — no reviewer is editing files while another reads them, and the wave rule has nothing left to sequence. `/review-slop` is excluded on cost, and the reason is worth stating honestly rather than as coverage: round one swept the branch as it stood *before* the fix commit existed, so the fix diff is exactly what its sweep did not see. That is a known, accepted gap in what a follow-up round covers, not a case already handled.
   - **No exemption for a small or cosmetic round.** A round whose edits only touched comments or documentation still gets a follow-up round. An unattended run asked to judge a fix "trivial" decides differently every time, and a comment that now misdescribes the code it sits above is exactly what a follow-up round is for.

   **How to brief a follow-up round.** Give it the diff range and the branch, and ask it **what the changed code used to do** and whether the change is sound on its own terms. Tell it the files are readable at HEAD and the previous state at the round's base (`git show <base>:<path>`), so it can judge the change against its surroundings rather than the diff hunk alone — the regression this loop exists to catch was a `catch` clause narrowed in isolation, where the question that exposes it is what the old clause used to absorb. Do **not** tell it which finding the change was answering, or that the change is believed to be a fix: a reviewer handed the conclusion tends to confirm it rather than test it.

   **Round one's reviewers and waves.** Spawn independent, clean-context reviewer subagents over the branch diff and run a `/review-slop` pass, in the two waves below. The clean-context subagents must not see the code being written — "do not inline the review" governs the *reviewing*. The *deciding-and-fixing* legitimately happens in `/verify`'s own main loop.
   - Spawn the `pr-review-toolkit` reviewers that apply to this diff, as independent, clean-context Task subagents. The `pr-review-toolkit:` prefix is required — the bare names do not resolve. Leave out any reviewer that does not apply (e.g. `pr-review-toolkit:type-design-analyzer` on a docs-only diff). They run in **two waves**:
     - **Wave 1 — the reporters, in parallel.** `pr-review-toolkit:code-reviewer`, `pr-review-toolkit:silent-failure-hunter`, `pr-review-toolkit:pr-test-analyzer`, `pr-review-toolkit:type-design-analyzer` and `pr-review-toolkit:comment-analyzer` only **report** findings. Launch them together, and run `/review-slop` (which emits a cleaned diff) while they work.
     - **Wave 2 — `pr-review-toolkit:code-simplifier`, alone, only after every wave-1 reviewer you launched and `/review-slop` have returned.** It is the one reviewer that **edits files directly**, so it must not run while anything is still reading the tree. If it does not apply to the diff, skip wave 2. While it runs you may aggregate and validate wave-1 findings, but make no edit to the working tree until it has returned. Wave-1 findings and the cleaned diff are anchored to HEAD: before applying one, relocate it in the current file, and drop any the simplifier's edits already resolved.
   - **Keep the waves — never run `code-simplifier` alongside the reporters.** They share one working tree, so a concurrent simplifier rewrites files the reporters are still reading, and their `file:line` anchors silently drift between the edited file and HEAD (observed in #265: reporters on the same finding cited `:27-28` and `:30-31`). Do not fix this instead by giving the simplifier its own worktree: step 3 finds review edits through `git status --porcelain`, and edits made in another worktree never show up there, so they would never be committed.

   **What the loop does with a round's findings.** In rounds one to three a finding from a follow-up round is validated and acted on exactly as a round-one finding is, with no discount for arriving late, and a confirmed blocker in a fix is as blocking as a confirmed blocker in the original code. Aggregate the returned findings, and in round one the cleaned diff as well (follow-up rounds run no `/review-slop` pass, so they have none). For each finding, first *validate it is real* — reviewer severities are fickle, so do not act on a mislabelled or false-positive finding. Then find its row in the table below by severity and scope, and its column by round. **The table and the definitions under it are the only statement of which outcome a finding gets;** step 3 says how round four's outcomes reach the verdict and the report.

   | Finding | Rounds one to three | Round four |
   |---|---|---|
   | Rejected as not real | Not acted on | Not material |
   | **Blocker / P1**, in scope | **Fix it** | **Material** |
   | **Blocker / P1**, out of scope | **Fix it** | Deferred |
   | **Important / P2**, in scope | **Fix it** | **Material** |
   | **Important / P2**, out of scope | Deferred | Deferred |
   | **Suggestion / P3**, any scope | Discretionary | Not applied |

   What the table's words mean:

   - **Blocker / P1** — a correctness bug, breakage, or anything that would ship broken.
   - **In scope** — the finding concerns the branch's own new or edited code, or breakage that code causes elsewhere. **Out of scope** — it concerns *pre-existing or adjacent* code the branch did not cause. If you are unsure which, treat it as in scope.
   - **Fix it** — fix it in the working tree. If a confirmed one genuinely cannot be fixed, **STOP and report**, naming the edits already applied for other findings this round and that they are uncommitted and unverified. Discarding those edits is the recovery, for the same reason as the red re-run in step 3: they are unverified, so committing them to satisfy step 0 on a later run puts unreviewed and untested code on the branch. Declining to fix one and leaving the tree empty is not a clean round.
   - **Deferred** — do **not** force-fix it here: in rounds one to three that folds an unrelated mission into the branch, and in round four nothing may be fixed. Name it in the final report as a deferred out-of-scope finding; in round four give its severity unchanged. In rounds one to three you may raise it as a follow-up issue instead. It does not block the verdict.
   - **Discretionary** — apply it if cheap and clearly correct, otherwise skip it.
   - **Material** — the run FAILS. Step 3 gives the verdict line and what the report must name.
   - **Not acted on**, **Not material**, **Not applied** — nothing is changed for it, and it does not block the verdict.

   In rounds one to three, apply the edits the table calls for to the working tree. Every applied edit is re-verified by step 3's suite re-run, so a bad fix cannot reach a PR green-unchecked.

   **In round four, nothing is applied — the findings are sorted, not acted on.** Validate each one exactly as in any other round (a false positive is still rejected on its merits), then read each survivor's cell in the round-four column. Nothing may be fixed in this round, which is why that column holds no **Fix it**.

   **Materiality rests on the reviewer's own rating, and you cannot lower it.** In round four a finding's row is set by its reviewers' ratings and nothing else: the Blocker or Important row when *any* reviewer rated it so, the Suggestion row otherwise. You may reject a finding as *not real* — that is a judgement about the facts, and reviewer severities are fickle. You may **not** re-rate a real Blocker or Important down to a Suggestion, nor decide a real one is "minor enough", nor narrow "the branch's own code" to exclude a file the branch edited, nor file breakage a reviewer attributes to the branch's change under *pre-existing or adjacent*, unless you have checked and can show it predates the branch. The whole point of the last round is that the thing deciding the verdict is not the thing that wants the run to finish, so a downgrade made to get through is the one failure mode that defeats it. The unsure-scope default matters most here: a human re-reading a sound fix costs one run, and a material problem reaching a pull request costs more.

   If a review subagent errors, STOP and report (stop-on-failure) — in round one, a wave-1 error means wave 2 is never launched.

3. **Re-verify, commit this round's edits, and decide whether another round runs — or, in the last round, rule on what it found.** Step 0 required a clean tree and every earlier round committed its own edits, so `git status --porcelain` now shows exactly what the round that just finished changed — from *any* source (the loop's own fixes **and**, in round one, any files `pr-review-toolkit:code-simplifier` edited directly) — and nothing else. Committing each round before the next begins is what keeps that invariant true all the way down the loop, and it is what gives each follow-up round a clean, exact diff to review.
   - **First, compare HEAD with the value noted when this round began (step 2).** Nothing but this step commits during a round, so if HEAD has moved, a reviewer committed its own edits — `git status --porcelain` does not show a commit, so neither branch below would see it, and the next round's range would start after it. **STOP and report**, naming every commit from the noted value to HEAD as unread and untested. This is the one stop that names commits other than a round's own fix commit. Say too that any uncommitted edits in the tree are this round's unverified fixes, that discarding them is the recovery, and that re-running `/verify` afterwards is what gets those stray commits read — round one reviews `git diff main...HEAD`, which contains them. If the noted value was lost, STOP and report that instead of assuming HEAD did not move.
   - **If this was round four (the last round, which only reads):** the tree must be clean — it made no edit. If `git status --porcelain` is non-empty, round four edited something it was told not to: **STOP and report** `FAILED reason=the last review round edited the branch`, naming the uncommitted edits and that discarding them is the recovery. Otherwise there is nothing to re-run and nothing to commit; the verdict is whatever step 2's sort produced:
     - **A material finding ⇒ STOP and report** `FAILED reason=last review round found a material problem`, **naming the finding** — which reviewer raised it, its severity, and where it is. The third round's fix stays committed and the tree stays clean: those edits are green and are real fixes, so reverting them would hand `/raise-pr` a worse branch than the one it was given. But the branch is **not** verified and the next thing that looks at it is a human. State the recovery: fix the named problem, then re-run `/verify`, which starts again at round one over `git diff main...HEAD`.
     - **No material finding ⇒ the branch is verified.** Go to step 4. Every fix on the branch has now been read by a reviewer that did not write it, including round three's. List round four's *Deferred* findings in the report **as findings left unfixed**, each by name and severity (the report is the only route by which a deferral reaches the PR body), and its *Not applied* ones as not applied. Do not quietly apply one "while you are here": that is the round-four edit the rule above forbids.
   - **If `git status --porcelain` is empty (the round changed nothing — rounds one to three only; round four is decided above):** the loop ends and the branch is verified. Skip the format pass, the re-run and the commit — go to step 4. (No spurious second suite run.) The last suite run was against exactly the committed code, and every change on the branch has now been read by a round that did not write it.
   - **If it is non-empty (the round applied edits — rounds one to three only):**
     - **Record this round's base, and which round this is** — `git rev-parse HEAD`, taken *before* the commit below. That is the range start the next round reviews from, and the round number is the other piece of loop state the branches below and step 2's round-four rule depend on. Record both explicitly, and if either is lost, **STOP and report**. Do not reconstruct the base from HEAD: `HEAD~1` happens to be correct immediately after this round's commit, but a range derived from the same HEAD it is meant to validate is never empty, so using it silently forfeits the empty-range check at the top of step 2 — the one guard that catches a mis-recorded base — and reconstructing it one round too late yields the wrong round's base with nothing to catch that either. Never guess, and never silently widen the range to `main...HEAD`, which would re-review cleared code and bury the fix diff inside it.
     - **Format this round's edits, before the suite re-run** — `dotnet format ./src/NetPace.sln`, the same bare command as step 1a and the same one CI checks. A review fix is written fast and is routinely off-format, and this is the only pass that ever sees it: step 1a ran before the fix existed. Formatting *here*, rather than after the commit, is what keeps two invariants true at once — the suite below runs on exactly the bytes that get committed, and the round's commit holds its fix and that fix's formatting together, so the next round reviews one coherent change instead of a fix now and a reformat later. A non-zero exit is a real failure ⇒ **STOP and report** `FAILED reason=dotnet format failed`; the tool merely rewriting files is not. If it changed nothing, that is the normal case for a fix that was already in format: make no separate commit and run no extra round for it.
     - Re-run `dotnet build ./src && dotnet test ./src`. Not green ⇒ STOP and report — and say that the tree is dirty, that the edits in it are this round's failed fix (and its formatting), and that discarding them is the recovery. Do **not** commit them to satisfy step 0's clean-tree precondition on a later run: that would put a red, unreviewed fix on the branch, which is the one thing this step exists to stop.
     - Once green, **commit the edits** with `git add -A` and a message naming the round, in the repo's `Refs #<N>: <imperative>` form — e.g. `Refs #328: apply /verify review findings (round 2)`, with the issue number read off the branch name and the round number substituted, not left as placeholders. If the branch name carries no issue number, drop the `Refs #<N>: ` prefix and keep the rest; the constitution requires it only where an issue applies. Commit immediately, with no further edit in between, so the suite run above was against exactly the code the commit contains. This is what makes the fixes reach the eventual PR — `/raise-pr` pushes *commits*, so uncommitted or untracked working-tree edits would silently never leave this machine. The gap between the fix and the push is open-ended, so an uncommitted edit can sit there indefinitely waiting to be lost. `git add -A` is correct and complete here precisely because the tree started clean: it stages every review edit and its formatting (including new untracked files and deletions) with no risk of sweeping in unrelated local changes.
     - **Go back to step 2 and run the next round** over `git diff <the base you just recorded>..HEAD`. If this was round three, that next round is round four, which only reads (step 2) — so there is always a round left to read the commit just made, and no commit `/verify` makes reaches step 4 unread. The bound is never hit with a fix outstanding, which is why there is no `review rounds did not converge` verdict any more and no `unreviewed` commit marker: both described a state the loop can no longer be in.

4. **Stop here.** Do **not** push, open a PR, merge, or run `/raise-pr`. Leave the working tree clean — everything committed to the branch — because that is exactly `/raise-pr`'s entry condition, so the two compose by hand with nothing in between.

## The two reviews (Review A vs Review B)

- **Review A** — steps 2 and 3, synchronous, in-`/verify`: the clean-context `pr-review-toolkit` subagents (plus `/review-slop` in round one), run in up to the four rounds step 2 bounds the loop at, the last of which only reads. Its findings drive the step-2 fixes and are committed in step 3 — that is how the review shapes the branch before a PR is ever raised.
- **Review B** — asynchronous, on the PR: the `@claude` GitHub-action review that `/raise-pr` requests when a human runs it. It is therefore outside `/verify` entirely, and nothing here waits on it. It is author-gated (`claude.yml`) so it doesn't even post for a non-`FrankRay78` invoker. Review B is for a human to read at merge; when you later run `/capture-learnings` at a supervised checkpoint, that command's own best-effort PR-review fetch picks it up then.

## Final report

Report, in this order:

- Whether formatting changed anything, and the commit if it did — step 1a's, and any round whose commit carried formatting alongside its fix.
- The suite result(s).
- **How many review rounds ran**, and for each round that applied edits, the commit it made. A run whose first round led to no edits reports one round. Say explicitly whether a last, read-only round ran and what it reported.
- Which review findings were fixed-and-committed, and — **named explicitly** — any confirmed finding deferred as an out-of-scope follow-up, plus any finding the last round raised and left unfixed (with its severity). This report is the only route by which a deferred finding reaches the PR body, because `/raise-pr` runs in a separate session; an unnamed deferral is a lost one.
- On the way to a `VERIFIED` verdict, add this **above the verdict line** — it is boilerplate this command mandates, and appending it below the verdict is the commonest way to lose the verdict: "Run `/raise-pr` to push the branch and open the PR — it derives `Closes #<N>` from this branch name and verifies it before use, then reports what it settled; check that line to confirm the link was made. The `@claude` Review B posts async on the raised PR, and `/capture-learnings` folds it in when you next review the batch."

**Close the report with the verdict on its own last line** — plain, at column 1, nothing else on that line and nothing after it. Exactly one of:

- `VERIFIED branch=<branch>` — on success.
- `FAILED reason=<short reason>` — on any failure.

Both are written bare, never inside a code fence: `scripts/chain.sh` reads the last non-blank line of the report, so a fence closing beneath the verdict is the last line and the verdict is lost. The fixed reasons this command emits are `last review round found a material problem` (step 3), `the last review round edited the branch` (step 3), `dotnet format failed` (step 1a or step 3) and step 0's three precondition reasons. Anything else is a short reason of your own.

That one line is the whole of what the chain reads, which is what makes it safe and what makes it strict:

- **Nothing may follow it.** Not a closing sentence, not a fence, not a blank-line-and-a-postscript. A report whose last line is anything but a verdict stops the chain as unreadable — a safe stop, but a wasted run.
- **Nothing above it can be mistaken for it.** Quote either verdict as often as the report needs to — `not VERIFIED`, a `FAILED reason=` a reviewer raised, a table of both — and it changes nothing. The rule that used to forbid writing the other verdict's word anywhere in the report is gone with the prose scanning that needed it.
- **Decoration on the verdict line is tolerated, not invited.** One leading heading, bullet, numbered-item or blockquote marker — one, not a stack — and a run of `*`, `_` or backticks wrapping the line, are stripped; so is an indent of up to three spaces. `Verdict: FAILED reason=…` is not a verdict, because the line must open with the verdict word, and neither is a line carrying anything *besides* the verdict: `VERIFIED branch=x (2 Important deferred)` is read as no verdict at all, not as a pass.

Never report verified over a red suite, a confirmed finding whose cell in step 2's table is **Fix it** or **Material** and that is still unresolved, a round-four *Deferred* Blocker the report does not name, an uncommitted change, or a committed change no review round read.
