---
description: Orchestrator that turns "implementation looks done" into a reviewed, test-green branch — runs the full suite first and hard-gates on it, then reviews in rounds until a round finds nothing to change, fixing every confirmed Blocker/Important finding and committing each round. Stops short of the pull request. Runs unattended, so it can drive a loop.
---

Read `CLAUDE.md` for project context before proceeding.

`/verify` is the stage between `/build` and `/raise-pr`: it turns a feature branch into a **formatted, test-green, reviewed, fully-committed** branch with a clean working tree. It does not push, open a PR, or merge — `/raise-pr` owns all of that, and you run it yourself afterwards.

`/verify` composes NetPace's existing commands behind one hard gate: **the full test suite gates everything downstream, and no review happens unless it is green.** The gate is structural — the review step is downstream of the step-1 exit code, so it cannot begin against un-verified or red code. Do not add a hook to police this ordering; the exit code *is* the gate. The one step that precedes the suite is formatting (step 1a), which is cosmetic and is itself covered by the gate that follows it.

**The review is a loop, not a single pass.** A fix written in response to a review is new code, written quickly against a reviewer's framing of the problem, and it often changes error handling — the riskiest code on the branch, and historically the only code on it that nothing but the suite ever read. So steps 2 and 3 repeat: each round reviews what the previous round committed, until a round finds nothing to change. A `VERIFIED` branch therefore contains no change that some reviewer who did not write it has not read.

`/verify` is designed to run to completion **without prompting**, so it can be driven by an automated loop (e.g. verifying many features back-to-back) as well as invoked directly. Reflection (`/capture-learnings`) is deliberately **not** a step: it needs human curation and batches better across many features, so it belongs at a supervised checkpoint after a batch — not inside each verify, where it would either block the loop or be auto-skipped to nothing.

Raising the pull request is deliberately **not** a step either. It is the one irreversible, outward-facing act in the chain: everything `/verify` does is safe to re-run, and pushing a branch and opening a PR is not. Keeping it a separate deliberate `/raise-pr` invocation is what makes the rest of the chain freely repeatable.

**Stop-on-failure is global:** if any step fails — the tree is dirty, a suite run is not green, a review subagent errors, the review rounds do not converge — STOP at that step, report it to the invoker, and do not run any later step. Two things belong in *every* such report once the loop has begun, not just the non-convergence one: the state of the working tree, and — **only where the latest commit is a round's own fix commit that no completed round read** — that commit named as a change no reviewer has read. Check before asserting it, because the stops differ: a reviewer erroring in round two leaves round one's commit genuinely unread, whereas a red re-run in round three leaves every round's commit already read and the *tree* dirty with the failed fix. The qualifier matters at the other end too: if a reviewer errors in round one, the latest commit is step 1a's format commit or whatever `/build` left, and naming that as an escape from the review loop would be misleading — round one's own diff covers it. Reporting a reviewed commit as unread is its own failure — it sends a human to re-read code two rounds already cleared, and makes the rest of the report less believable.

## Steps

0. **Preconditions (before any suite run or review).**
   - Run `git rev-parse --abbrev-ref HEAD`. If it is `main`, STOP immediately and report: "Run /verify from a feature branch, not main." Do not run the suite, do not spawn reviewers.
   - Run `git log main..HEAD --oneline`. If empty, STOP immediately and report: "No commits on this branch over main — nothing to verify." Do not run the suite or spawn reviewers.
   - Require a **clean working tree**. Run `git status --porcelain`; if it is non-empty, STOP and report: "Commit or stash your changes before verifying." A clean tree is what makes step 3 simple and correct: after the review, *anything* that shows up in the tree is a review edit and nothing else, so there is no need to separate review edits from pre-existing local changes.

   The first two checks run up front purely on cost grounds: a full format, a full suite run and a full review are minutes of work, and on `main` or an empty branch every one of those minutes is spent to reach a conclusion a cheap `git` call already had. The clean-tree check earns its place differently — it is the invariant that makes step 3 correct, as described above.

1. **Format (1a), then the full test run (1b).**

   **1a — Format the tree.** Run:

   ```bash
   dotnet format style ./src/NetPace.sln && dotnet format whitespace ./src/NetPace.sln
   ```

   The explicit `./src/NetPace.sln` argument is **required, not decorative**: `dotnet format` looks for a project or solution in the *current directory only*, and NetPace's solution is at `src/`, not the repo root. Omitting it fails with `Could not find a MSBuild project file or solution file`.

   - Formatting runs **once per verify**, not per commit. It is cosmetic work at a cadence that already costs minutes — see *Formatting is not verification* in [agentic-workflow.md](../../docs/agentic-workflow.md).
   - **If formatting changed files, commit them now** — `git add -A` and a message in the same `Refs #<N>: <imperative>` form step 3 uses, e.g. `Refs #328: apply dotnet format` — *before* running the suite. This restores the clean working tree step 0 established, which is what keeps step 3's "anything in the tree is a review edit" invariant true. Do not carry format edits forward into the review commit; they are a separate concern and belong in their own commit.
   - A **non-zero exit** from `dotnet format` is a real failure (bad workspace argument, unparseable source) ⇒ **STOP and report**. A clean run that merely rewrote files is not a failure.
   - Formatting deliberately precedes 1b so that any change it makes is verified by the suite below, rather than landing after the gate has already passed.

   **1b — Full test run (always).** Run `dotnet build ./src && dotnet test ./src` — always, including docs-only branches. Do not add a skip path for docs-only branches: the suite is fast, and this is the first whole-suite gate after `/build`, whose run precedes formatting and review fixes. The `gh pr create` `PreToolUse` hook re-runs the suite, but that hook fires inside a separately invoked `/raise-pr` that may not happen for a long while, or at all — so skipping here would leave a branch reported verified that no suite ever ran against.
   - Gate on the run's **exit code**, not on any stored marker.
   - **Not green ⇒ STOP:** report the failures to the invoker and do nothing else — no review subagents.
   - **Green ⇒ continue.**

2. **Review round (synchronous — this is Review A).** Steps 2 and 3 are a loop: a round reviews a diff, the loop applies and commits what that review warrants, and the next round reviews what the last one committed. **The round bound is three rounds in total, round one included** — nothing in `/verify` reviews beyond that, and that bound is what makes the loop terminate. Round one is the review `/verify` has always run; a branch that needed a fix needs a second round to read that fix; a third absorbs one bad fix. Past the bound the fixes are not converging and a human should look (step 3).

   **What this round reviews.**
   - **Round one** — the whole branch diff, `git diff main...HEAD`.
   - **A follow-up round** — only what the previous round committed, `git diff <that round's base>..HEAD`, where *the round's base* is the commit HEAD pointed at before step 3 committed that round's edits. Step 3 records it, so a follow-up round reviews an exact diff rather than guessing at one from the log.
   - **An empty follow-up range is a bookkeeping failure, not a clean round.** Check the range is non-empty before briefing anyone; if it is empty, the base is wrong — most likely taken after step 3's commit instead of before it — and the reviewers would be handed nothing, truthfully report nothing, and leave the previous round's commit read by no one while the run reported `VERIFIED`. That is the exact failure this loop exists to prevent, so **STOP and report** rather than treating a review of zero lines as convergence.

   **Who reviews.**
   - **Round one — the full applicable set, in two waves**, exactly as below.
   - **A follow-up round — a narrower set over the fix diff only, in a single parallel wave:** `pr-review-toolkit:code-reviewer` and `pr-review-toolkit:silent-failure-hunter` always, plus three conditional on what the round actually touched — `pr-review-toolkit:pr-test-analyzer` for a test file, `pr-review-toolkit:comment-analyzer` for a comment or a documentation file, and `pr-review-toolkit:type-design-analyzer` for a new or changed type. Decide all three off the round's own `git diff <base>..HEAD` rather than from memory of what you edited: the file list settles the documentation case, but a comment or a type can change inside a file whose name says nothing, so read the diff content and not just `--name-only`.
   - **Only `pr-review-toolkit:code-simplifier` and `/review-slop` are excluded outright**, as against the three above whose conditions may simply not be met. `code-simplifier` is excluded structurally: it is the one reviewer that edits files, so leaving it out is what means there is **no wave 2 in a follow-up round** — no reviewer is editing files while another reads them, and the wave rule has nothing left to sequence. `/review-slop` is excluded on cost, and the reason is worth stating honestly rather than as coverage: round one swept the branch as it stood *before* the fix commit existed, so the fix diff is exactly what its sweep did not see. That is a known, accepted gap in what a follow-up round covers, not a case already handled.
   - **No exemption for a small or cosmetic round.** A round whose edits only touched comments or documentation still gets a follow-up round. An unattended run asked to judge a fix "trivial" decides differently every time, and a comment that now misdescribes the code it sits above is exactly what a follow-up round is for.

   **How to brief a follow-up round.** Give it the diff range and the branch, and ask it **what the changed code used to do** and whether the change is sound on its own terms. Tell it the files are readable at HEAD and the previous state at the round's base (`git show <base>:<path>`), so it can judge the change against its surroundings rather than the diff hunk alone — the regression this loop exists to catch was a `catch` clause narrowed in isolation, where the question that exposes it is what the old clause used to absorb. Do **not** tell it which finding the change was answering, or that the change is believed to be a fix: a reviewer handed the conclusion tends to confirm it rather than test it.

   **Round one's reviewers and waves.** Spawn independent, clean-context reviewer subagents over the branch diff and run a `/review-slop` pass, in the two waves below. The clean-context subagents must not see the code being written — "do not inline the review" governs the *reviewing*. The *deciding-and-fixing* legitimately happens in `/verify`'s own main loop.
   - Spawn the `pr-review-toolkit` reviewers that apply to this diff, as independent, clean-context Task subagents. The `pr-review-toolkit:` prefix is required — the bare names do not resolve. Leave out any reviewer that does not apply (e.g. `pr-review-toolkit:type-design-analyzer` on a docs-only diff). They run in **two waves**:
     - **Wave 1 — the reporters, in parallel.** `pr-review-toolkit:code-reviewer`, `pr-review-toolkit:silent-failure-hunter`, `pr-review-toolkit:pr-test-analyzer`, `pr-review-toolkit:type-design-analyzer` and `pr-review-toolkit:comment-analyzer` only **report** findings. Launch them together, and run `/review-slop` (which emits a cleaned diff) while they work.
     - **Wave 2 — `pr-review-toolkit:code-simplifier`, alone, only after every wave-1 reviewer you launched and `/review-slop` have returned.** It is the one reviewer that **edits files directly**, so it must not run while anything is still reading the tree. If it does not apply to the diff, skip wave 2. While it runs you may aggregate and validate wave-1 findings, but make no edit to the working tree until it has returned. Wave-1 findings and the cleaned diff are anchored to HEAD: before applying one, relocate it in the current file, and drop any the simplifier's edits already resolved.
   - **Keep the waves — never run `code-simplifier` alongside the reporters.** They share one working tree, so a concurrent simplifier rewrites files the reporters are still reading, and their `file:line` anchors silently drift between the edited file and HEAD (observed in #265: reporters on the same finding cited `:27-28` and `:30-31`). Do not fix this instead by giving the simplifier its own worktree: step 3 finds review edits through `git status --porcelain`, and edits made in another worktree never show up there, so they would never be committed.

   **What the loop does with a round's findings — every round, round one and follow-ups alike.** A finding from a follow-up round is validated and acted on exactly as a round-one finding is, with no discount for arriving late, and a confirmed blocker in a fix is as blocking as a confirmed blocker in the original code. Aggregate the returned findings, and in round one the cleaned diff as well (follow-up rounds run no `/review-slop` pass, so they have none). For each finding, first *validate it is real* — reviewer severities are fickle, so do not act on a mislabelled or false-positive finding — then act by severity:

   - **Blocker / P1** (a correctness bug, breakage, or anything that would ship broken) — **must be resolved.** Fix it in the working tree. If a confirmed blocker genuinely cannot be fixed, **STOP and report**, naming the edits already applied for other findings this round and that they are uncommitted and unverified. Discarding those edits is the recovery, for the same reason as the red re-run below: they are unverified, so committing them to satisfy step 0 on a later run puts unreviewed and untested code on the branch. `/verify` never reports a branch verified over a known blocker.
   - **Important / P2** — fix it **when it is within the scope of this change** (the branch's own new or edited code). If a confirmed P2 concerns *pre-existing or adjacent* code the branch did not cause, do **not** force-fix it here — that folds an unrelated mission into the branch; name it in the final report as a deferred out-of-scope finding, or raise it as a follow-up issue.
   - **Suggestion / P3** — discretionary: apply if cheap and clearly correct, otherwise skip.

   Apply the warranted edits to the working tree. Every applied edit is re-verified by step 3's suite re-run, so a bad fix cannot reach a PR green-unchecked.

   If a review subagent errors, STOP and report (stop-on-failure) — in round one, a wave-1 error means wave 2 is never launched.

3. **Re-verify, commit this round's edits, and decide whether another round runs.** Step 0 required a clean tree and every earlier round committed its own edits, so `git status --porcelain` now shows exactly what the round that just finished changed — from *any* source (the loop's own fixes **and**, in round one, any files `pr-review-toolkit:code-simplifier` edited directly) — and nothing else. Committing each round before the next begins is what keeps that invariant true all the way down the loop, and it is what gives each follow-up round a clean, exact diff to review.
   - **If `git status --porcelain` is empty (the round changed nothing):** the loop ends and the branch is verified. Skip both the re-run and the commit — go to step 4. (No spurious second suite run.) The last suite run was against exactly the committed code, and every change on the branch has now been read by a round that did not write it.
   - **If it is non-empty (the round applied edits):**
     - **Record this round's base, and which round this is** — `git rev-parse HEAD`, taken *before* the commit below. That is the range start the next round reviews from, and the round number is the other piece of loop state the bound decisions below depend on. Record both explicitly, and if either is lost, **STOP and report**. Do not reconstruct the base from HEAD: `HEAD~1` happens to be correct immediately after this round's commit, but a range derived from the same HEAD it is meant to validate is never empty, so using it silently forfeits the empty-range check at the top of step 2 — the one guard that catches a mis-recorded base — and reconstructing it one round too late yields the wrong round's base with nothing to catch that either. Never guess, and never silently widen the range to `main...HEAD`, which would re-review cleared code and bury the fix diff inside it.
     - Re-run `dotnet build ./src && dotnet test ./src`. Not green ⇒ STOP and report — and say that the tree is dirty, that the edits in it are this round's failed fix, and that discarding them is the recovery. Do **not** commit them to satisfy step 0's clean-tree precondition on a later run: that would put a red, unreviewed fix on the branch, which is the one thing this step exists to stop.
     - Once green, **commit the edits** with `git add -A` and a message naming the round, in the repo's `Refs #<N>: <imperative>` form — e.g. `Refs #328: apply /verify review findings (round 2)`, with the issue number read off the branch name and the round number substituted, not left as placeholders. If the branch name carries no issue number, drop the `Refs #<N>: ` prefix and keep the rest; the constitution requires it only where an issue applies. Decide the message *here*, before committing: the round number is recorded above, so you already know whether the bound allows another round, and if it does not, this commit is the one no round will read — so write it as `(round <n>, unreviewed)`. That marker is the only durable trace that *this* branch's last commit went unreviewed, and after the commit it can no longer be added without an amend this procedure does not authorise. It is not a general signal that a branch is clean: a reviewer erroring mid-loop also leaves an unread commit, and that one never gets a marker, which is why the report and not the marker is the authoritative record. Commit immediately, with no further edit in between, so the suite run above was against exactly the code the commit contains. This is what makes the fixes reach the eventual PR — `/raise-pr` pushes *commits*, so uncommitted or untracked working-tree edits would silently never leave this machine. The gap between the fix and the push is open-ended, so an uncommitted edit can sit there indefinitely waiting to be lost. `git add -A` is correct and complete here precisely because the tree started clean: it stages every review edit (including new untracked files and deletions) with no risk of sweeping in unrelated local changes.
     - **If the round bound allows another round:** go back to step 2 and run a follow-up round over `git diff <the base you just recorded>..HEAD`.
     - **If that was the last round the bound allows:** the rounds have not converged, and the commit above should already carry the `unreviewed` marker. STOP and report `FAILED reason=review rounds did not converge`, naming that commit as the change no round read and listing any finding left open or deferred beneath it. Its edits stay committed and the tree stays clean — unlike the red re-run above, these edits are green and are real fixes, so reverting them would hand `/raise-pr` a branch in a worse state than the one it was given — but the branch is **not** verified, and the next thing that looks at it is a human. State the recovery too: re-running `/verify` starts again at round one over `git diff main...HEAD`, which does read that commit. Before stopping, confirm the commit above actually carries the `unreviewed` marker; if it does not, say so explicitly in the report, since it cannot be added afterwards and its absence would otherwise read as convergence.

4. **Stop here.** Do **not** push, open a PR, merge, or run `/raise-pr`. Leave the working tree clean — everything committed to the branch — because that is exactly `/raise-pr`'s entry condition, so the two compose by hand with nothing in between.

## The two reviews (Review A vs Review B)

- **Review A** — steps 2 and 3, synchronous, in-`/verify`: the clean-context `pr-review-toolkit` subagents (plus `/review-slop` in round one), run in rounds up to the step-2 bound. Its findings drive the step-2 fixes and are committed in step 3 — that is how the review shapes the branch before a PR is ever raised.
- **Review B** — asynchronous, on the PR: the `@claude` GitHub-action review that `/raise-pr` requests when a human runs it. It is therefore outside `/verify` entirely, and nothing here waits on it. It is author-gated (`claude.yml`) so it doesn't even post for a non-`FrankRay78` invoker. Review B is for a human to read at merge; when you later run `/capture-learnings` at a supervised checkpoint, that command's own best-effort PR-review fetch picks it up then.

## Final report

**Open the report with the verdict on its own first line, undecorated, at column 1**, with nothing before or after it on that line. Write exactly one of these two — on success:

```
VERIFIED branch=<branch>
```

or, on any failure:

```
FAILED reason=<short reason>
```

For non-convergence the reason is the fixed `review rounds did not converge`. The plain form is required because `scripts/chain.sh` scans for a `FAILED` verdict anchored to the start of a line — deliberately, so that `/study` quoting the phrase in prose cannot abort a healthy run. A leading bullet or quote marker is tolerated on its own (`- FAILED reason=…` and `> FAILED reason=…` both match); what breaks the scan is decoration touching the verdict itself. Missed outright: `- **FAILED reason=…**`, `**FAILED** reason=…`, backticks around the phrase, and a double space between the two words. And `**FAILED reason=x**` matches but captures the reason as `x**`. A missed verdict costs you the reason — the chain reports the far less useful `no recognisable verdict` instead.

Two further rules follow from how the success scan works. It is unanchored and matches anywhere in the report, so decoration *around* the pair survives (`**VERIFIED branch=x**`) but decoration *between* the two words does not (`VERIFIED **branch**=x` misses — the failure that once parked a verified #242). More importantly, it does not care about context: `not VERIFIED branch=x` matches. So **never write the other verdict's string anywhere in the report** — a `FAILED` report that mentions `VERIFIED branch=` in its prose, and whose own verdict line is decorated enough to be missed, is read by the chain as a success, and `/raise-pr` then opens a real pull request off a red or non-converged branch. Never report verified over a red suite, an unresolved confirmed blocker, an uncommitted change, or a committed change no review round read.

Then, beneath that line:

- Whether formatting changed anything, and the commit if it did.
- The suite result(s).
- **How many review rounds ran**, and for each round that applied edits, the commit it made. A run whose first round led to no edits reports one round.
- Which review findings were fixed-and-committed, and — **named explicitly** — any confirmed finding deferred as an out-of-scope follow-up. This report is the only route by which a deferred finding reaches the PR body, because `/raise-pr` runs in a separate session; an unnamed deferral is a lost one.
- On a `VERIFIED` verdict, follow with: "Run `/raise-pr` to push the branch and open the PR — it derives `Closes #<N>` from this branch name and verifies it before use, then reports what it settled; check that line to confirm the link was made. The `@claude` Review B posts async on the raised PR, and `/capture-learnings` folds it in when you next review the batch."
