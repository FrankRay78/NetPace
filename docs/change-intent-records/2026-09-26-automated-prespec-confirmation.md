# Confirming the Pre-Specification Review from a Label

**Intent:** Close the issue gate from the same place the answers were written. `/reviewissue` already ran unattended on a label, and the answers are typed into the GitHub UI, often away from the desk — but folding them in still needed a checkout. Labelling an issue `confirm` now runs `/confirmissue` in CI, so the whole gate happens on github.com.

**Behaviour:** [`.github/workflows/confirmissue.yml`](../../.github/workflows/confirmissue.yml), whose comments carry the decisions; `docs/agentic-workflow-NetPace.md` → *The whole pre-build issue gate runs in CI* for the gate as a whole.

**Known residuals** — the ones no workflow comment carries:

- **Nothing lints these workflows in CI.** `actionlint` was run locally against this change and found the two issue-gate workflows clean; it is wired into no job, so the next edit is unguarded. Constitution §I's carve-out asks for more than that: where the tool can run in CI it must, so the invariant is gated rather than verified once. Wiring it would immediately fail on a pre-existing `release-binaries.yml` finding (`softprops/action-gh-release@v1` on an unsupported runner), which is why it was not folded in here.
- **A queued run cancelled by the shared concurrency group is silent.** GitHub holds only one pending run per group, so a third trigger on an issue cancels the second, and a cancelled run notifies nobody — the issue keeps its label with no run behind it. Sharing one group across both issue-gate workflows roughly doubles each group's population, so this is the cost that choice buys.
- **The surviving-sentinel post-condition is stricter than the command's own contract.** It fails on *any* `<!-- speckit:review -->` comment, while the command resolves and deletes only the newest — a multi-comment case its prose explicitly anticipates. Scoping the check to the comment the run actually folded would mean plumbing that comment's id out of the agent step, which is more machinery than the case warrants.
- **The label-repair path can end red on an issue that is otherwise fine.** Where a previous run saved decisions but lost `ready`, the command re-applies the label and stops; if `needs answers` is still on, the post-condition fails on an issue whose decisions are safely saved. The asymmetry is deliberate and worth revisiting: the review workflow *applies* `needs answers` itself rather than trust the model, while this one trusts the model to *remove* it and fails the run when it forgets. Removing it in the post-condition instead (`gh issue edit --remove-label`, a no-op when absent) would delete this residual, at the cost of reversing a confirmed decision.
- **Untrusted issue content reaches the model while it holds `issues: write`, and this run writes the body.** The label gate is the mitigation, as it is for the review workflow, but the blast radius of a successful injection is larger here: it could rewrite the proposal rather than only comment on it.
