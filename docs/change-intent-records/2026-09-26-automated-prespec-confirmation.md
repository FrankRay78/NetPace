# Confirming the Pre-Specification Review from a Label

**Intent:** Close the pre-spec gate from the same place the answers were written. `/speckit.reviewissue` already runs unattended on a label; the answers are typed into the GitHub UI, often away from the desk; and then folding them in still needed a checkout. Labelling an issue `confirm` now runs `/speckit.confirmissue` in CI, so the whole gate — request, answer, confirm — happens on github.com.

**Supersedes:** the scope clause of [`2026-09-07-automated-prespec-review`](2026-09-07-automated-prespec-review.md), whose intent reads "answering the questions and running `/speckit.confirmissue` are quick by comparison and stay local". Quick was true and beside the point: confirmation was the one step still tied to a checkout, which is what actually decided where the gate could be finished. Everything else in that record stands, and this workflow deliberately mirrors it.

**Behaviour:**
- Given: an issue with a posted review where every gap has a non-hedging answer, and the `FrankRay78` account
- When: that account applies the `confirm` label
- Then: the issue body gains a `## Confirmed decisions` section, the issue is labelled `ready` and no longer `needs answers`, the review comment is gone, and the `confirm` label is cleared.
- Given: an issue whose review has an unanswered or hedging gap, or which has no review at all
- When: the `confirm` label is applied
- Then: the issue body, its labels and its review comment are exactly as they were; the `confirm` label stays on; the run is red and its summary names the gaps that need attention. No comment is posted on the issue.
- Given: an issue that already carries `ready`, with no review comment left on the thread
- When: the `confirm` label is applied
- Then: the agent does not run, nothing about the issue changes except that `confirm` is cleared, and the run is green.
- Given: an issue that carries `ready` but still has a `<!-- speckit:review -->` comment on the thread
- When: the `confirm` label is applied
- Then: the agent does not run, nothing about the issue changes, `confirm` stays on, and the run is red naming the comment that needs deleting.
- Given: a confirmation that saved the decisions but could not apply `ready`, could not remove `needs answers`, or could not delete the review
- Then: the run is red and names every half that is missing, and `confirm` stays on.
- Given: any account other than `FrankRay78` applies `confirm`
- Then: no run is created and nothing is confirmed.
- Given: a review or confirm run already in progress on an issue
- When: another of either is triggered on the same issue
- Then: it queues behind the first rather than running alongside it.
- Given: a change to this workflow or to the command on a branch
- When: the workflow is manually dispatched against that branch for a chosen issue
- Then: the branch's copy of both runs.

**Constraints:**
- The confirmation logic must stay single-sourced in [`.claude/commands/speckit.confirmissue.md`](../../.claude/commands/speckit.confirmissue.md), which is applied as written and unchanged by this record. A workflow that restates it forks the logic and the two copies drift.
- The repository is public, so the trigger must gate on the account that *applied* the label, not the account that raised the issue.
- Three operations across the command's steps 6 and 7 are never fatal — applying `ready`, removing `needs answers`, and deleting the review all report rather than fail, because by then the decisions are already saved and the command's chat report is the operator's signal. Only two of the three are stated as such: step 6's "Never fatal" bullet speaks to the label being *applied*, and the `needs answers` removal alongside it is covered by inference rather than by the single source. In CI there is no operator reading chat, so something else has to turn those reports into a run colour.
- The deletion in the command's step 7 is irreversible and silent. Nothing in this workflow may run ahead of the command's own hard-stops or ordering.
- On the `issues` path a run uses the default branch's copy of the workflow and of every file it reads, so a change to the command takes effect on merge, not on branch — and no event can trigger a *new* workflow file from a feature branch at all.

**Decisions:**
1. **A new workflow file, mirroring `speckit-reviewissue.yml` rather than extending it** — the two fail independently, run on different labels, and carry unrelated prompts; the confirm path also has no snapshot step and a four-condition post-condition the review path does not want. Folding them together would mean one file with two mutually-exclusive halves and an `if:` guarding each step. Rejected: a second job in the review workflow.
2. **One repo-wide concurrency group, `speckit-issue-<n>`, shared with the review workflow** — the two write the same state from opposite ends. A review posting mid-confirmation lands on top of decisions being saved; a confirmation running mid-review resolves the wrong comment, or none. Concurrency groups are repo-wide, so a shared *name* is the whole mechanism — which is why the review workflow's `speckit-reviewissue-<n>` had to be renamed, not merely matched in spirit. `cancel-in-progress: false` for the same reason the review workflow uses it: cancelling could kill a confirmation between its body patch and its label, manufacturing the split state the post-condition exists to catch.
3. **No issue snapshot step, unlike the review workflow** — that workflow snapshots because the action strips HTML comments from injected context, which would remove the `<!-- speckit:review -->` sentinel. This command never reads injected context: it resolves the review over REST itself, because step 7 deletes by *numeric* comment id and `gh issue view --json comments` returns the GraphQL node id instead. The sentinel therefore reaches it through its own call, intact, and a snapshot step would be a second source of the same truth. Rejected: copying the snapshot across for symmetry.
4. **A deterministic post-condition step, checking four conditions, is what decides the run's colour** — `anthropics/claude-code-action@v1` exits successfully whenever the model finishes its turn, so a never-fatal label failure is tool output the model reasons about, not a step failure. Without this step the exact half-finished states the command is designed to report would go green and notify no one. The four conditions are the command's own end-state contract read back off the issue: `## Confirmed decisions` on the body, `ready` on, `needs answers` off, and no surviving sentinel comment. This is decision 5 of the 2026-09-07 record applied to a command with three non-fatal steps instead of one.
5. **Every condition is evaluated before the step exits** — a first-failure exit would name one missing half and hide the rest, and these failures cluster: a run whose label call failed has usually also skipped the deletion that the label gates. One run should name everything that needs repair.
6. **Removing `confirm` is the last thing a green run does; a still-labelled issue is the "did not complete" signal** — this is decision 4 of the 2026-09-07 record, unchanged, transposed onto the second label. GitHub's failed-run notification is the alert. Rejected: posting a failure comment on the issue — noise on the issue for a signal GitHub already sends, and on the hard-stop paths it would land on an issue the run deliberately left untouched.
7. **The command's chat report goes to `$GITHUB_STEP_SUMMARY`, not to a comment** — the report is the only place the gap numbers and titles appear, and on a stop it *is* the alert, so it cannot be discarded. The step is `if: always()` precisely because the paths that need it most are the ones that end red. Writing it via the Write tool to a file, rather than having the model echo it, keeps a multi-line markdown report out of shell quoting.
8. **The already-confirmed guard is a workflow step, not a prompt instruction** — a model can skip an instruction. What the guard buys is *not* a green run: a genuinely confirmed issue satisfies all four post-conditions unaided, so removing the guard would leave that scenario green. It buys a skipped twenty-minute agent turn, it keeps untrusted issue content away from an `issues: write` token, and it is where the one state that looks confirmed but is not — `ready` with a surviving review comment — is turned red instead of skipped. The guard is deliberately *narrower* than the command's own already-confirmed stop, which fires on the decisions section or the label; this reads the label only. Both its reads are live, not snapshotted: a local `/speckit.confirmissue` is a second writer to the same state.
    - The surviving-comment case exists because step 7 saves the decisions and applies `ready` before a deletion that is never fatal. Skipping it green would turn the command's documented recovery — "re-running `/speckit.confirmissue #N` will retry it" — into a silent no-op in CI, since re-labelling arrives at this guard. Letting the agent run instead would fold a second decisions section, and deleting the comment from the workflow would put it ahead of the command's own ordering, which the constraints forbid. Stopping and naming the repair is the only move left.
9. **`id-token: write` alongside `contents: read` and `issues: write`** — `id-token: write` is granted by every `anthropics/claude-code-action@v1` use in the repository; the other two are the narrowest pair this workflow actually needs, and `claude.yml` grants a wider set for its own reasons. An unexplained divergence on the token line costs more to audit than the narrowest possible grant saves.
10. **The `gh api` allowlist is not narrowed by method or path** — `--allowedTools` *adds* to the rules Claude Code loads from the checked-out [`.claude/settings.json`](../../.claude/settings.json), which already grants `Bash(gh:*)`, so a narrower entry here would bound nothing while reading as though it did. The entries are listed for readability: they say what the run is *expected* to reach for. The token's `issues: write` scope is the real bound. Rejected: narrowing the entry (false assurance); changing `.claude/settings.json` (governs every local session too — separate work).
11. **`timeout-minutes: 30`, consistent with `speckit-reviewissue.yml`** — standard runners are free on a public repository, so only a hung job is worth guarding, and confirmation is the cheaper of the two passes anyway.

**Known residuals:**
- **Pre-merge verification is limited to what a branch can run.** GitHub registers `workflow_dispatch` only from the default branch, so a *new* workflow file cannot be dispatched against a feature branch — the same constraint decision 9 of the 2026-09-07 record recorded. The evidence available before merge is that the file lints clean (`actionlint` + `shellcheck`) and that the `confirm` trigger and shared concurrency group exist where nothing responded to the label before. The behaviour clauses above are verified after merge, against a throwaway issue; `workflow_dispatch` earns its place afterwards, for the next prompt tweak.
- **A correct stop and a genuine breakage are both red, and look alike from the Actions tab.** An unanswered gap is the command working exactly as designed, but it fails the post-condition just as a crashed run does. The run summary is what distinguishes them, and it is only as good as the report the model wrote. Accepted: the alternative is teaching the workflow to parse the command's stop reasons, which forks the logic decision 1 exists to keep single-sourced.
- **`confirm` applied by any other account is silent.** The job-level `if:` means GitHub creates no run at all, so nothing appears in the Actions tab and no notification is sent. The resulting state — labelled, nothing confirmed — is the same one decision 6 reserves for a failed run, but with no alert behind it. Identical to the review workflow's residual.
- **The tool allowlist narrows nothing.** Per decision 10, the run's real grant is every `gh` subcommand, not the six named entries, and the prompt's "do not post a comment on the issue" is a request rather than an enforced boundary.
- **Untrusted issue content reaches the model while it holds `issues: write`.** The command reads the issue body and its comments directly, and on a public repository both are attacker-authorable. The label gate is the mitigation: content only reaches the model if the maintainer deliberately labels the issue. Unlike the review workflow this run also *writes* the issue body, so the blast radius of a successful injection is larger — it could rewrite the proposal rather than only comment on it.
- **A queued run cancelled by the shared concurrency group is silent.** GitHub holds only one pending run per group, so a third trigger on an issue cancels the second, and a cancelled run sends no notification. The issue keeps its label with no run behind it — the state decision 6 reserves for a failure, minus the alert. Sharing the group across both workflows (decision 2) is right for the reason given there, and it roughly doubles the population of each group, so this is the cost that choice buys. Accepted for now: the state is self-describing, so a guard could later detect "labelled with no completed run".
- **The surviving-sentinel post-condition is stricter than the command's own contract.** The check fails on *any* `<!-- speckit:review -->` comment, while step 1 of the command resolves and step 7 deletes only the newest (`max_by(.created_at)`) — a multi-comment case the command's prose explicitly anticipates. An issue carrying two sentinel comments therefore ends red after a confirmation that did everything asked of it. Not narrowed, because scoping the check to the comment the run actually folded would mean plumbing that comment's id out of the agent step and into the post-condition, which is more machinery than the case warrants.
- **The label-repair path can end red on an issue that is otherwise fine.** Where a previous run saved decisions but lost `ready`, step 1 of the command re-applies the label and stops. If `needs answers` is still on at that point the post-condition fails, on an issue whose decisions are safely saved. Recoverable by removing the label and re-running; noisy in the meantime.
  - This is where the design is asymmetric with its sibling, and the asymmetry is deliberate but worth revisiting. #304 made the review workflow *apply* `needs answers` itself rather than trust the model, because the command file's instruction to add it was skipped on the first CI run that carried it (#296). This workflow trusts the model with the *removal* of the same label and fails the run when the model forgets — the opposite policy on the same label, one workflow apart. Built as #306's confirmed decisions specify. Removing it in the post-condition instead (`gh issue edit --remove-label`, a no-op when absent) would delete this residual and reduce the four conditions to three, at the cost of reversing a confirmed decision.
- **Nothing lints these workflows in CI.** `actionlint` was run locally against this change and found the two speckit workflows clean; it is not wired into any job, so the next edit is unguarded. `release-binaries.yml` already carries a finding (`softprops/action-gh-release@v1` on an unsupported runner) that no gate would have let through. Constitution I's carve-out asks for more than this: where the tool can run in CI it must, so the invariant is gated rather than verified once — and this branch's whole RED-GREEN evidence is a locally-run tool. Deferred rather than folded in here, because wiring the gate would immediately fail on that pre-existing `release-binaries.yml` finding, which is a separate mission. **A tracking issue still needs raising**; the same gap was accepted once already on the shell-tests branch (`docs/study/296.md`), and two accepted residuals for one missing gate is where it stops being a residual.
