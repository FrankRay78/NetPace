# Every pull request closes an issue

**Intent:** Make the issue the specification in fact rather than by convention. Work was reaching `main` through pull requests that named no issue, so the chain from acceptance criteria to merged code had a hole at its last hop — and a direct push by a repository admin could skip the pull request entirely. The goal is one gate that refuses a pull request which will not close an issue when it merges, binding everyone.

**Behaviour:**

- Given a pull request whose body carries a closing keyword naming an existing, open issue in this repository, when the `issue-link` job runs, then it passes and names the issue it linked to.
- Given a pull request whose body names an issue only as a bare `#N`, or only through the Development sidebar, or only inside a fenced block or inline-code span, when the job runs, then it fails and says no closing keyword names an open issue.
- Given a pull request whose body closes a number that does not exist, is a pull request, or is already closed, when the job runs, then it fails and reports each rejected reference with the reason it was rejected.
- Given a pull request authored by `dependabot[bot]`, when the job runs, then it passes without reading the body.
- Given GitHub cannot be reached, or a tool is missing, or the body cannot be read, when the job runs, then it fails with wording that distinguishes an outage from a body carrying no link.

**Constraints:**

- The confirmed decisions fix four things that were not open to reinterpretation: a closing keyword is what "linked" means, `dependabot[bot]` is the only exemption, no bypass actors is the required end state, and zero approving reviews are required.
- The fixed job name `issue-link` is the required-status-check context, so it lives in its own workflow where a change to the .NET matrix or the shell-test discovery cannot rename it out from under the ruleset.
- The gate must not be satisfiable by a skipped job: to GitHub a skipped job is not a failure, and `pull_request` workflows are evaluated from the head ref, so a `paths:` filter or an `if:` would let the branch adding it be the branch it stops gating.
- A pull request body is author-controlled content, so it reaches the check through the environment and is never interpolated into shell text.

**Decisions:**

**The keyword set is GitHub's nine forms, not the issue's three.** The confirmed decision names `Closes`/`Fixes`/`Resolves`. The check accepts `close`/`closes`/`closed`, `fix`/`fixes`/`fixed` and `resolve`/`resolves`/`resolved`, in any case. *Rejected: honouring literally the three spellings named.* The property the gate exists to guarantee is that merging closes an issue, and GitHub decides which spellings do that. `Fixed #332` genuinely links and closes, so rejecting it would fail a correctly-linked pull request — the decision's parenthetical reads as naming the canonical spellings, not as narrowing the grammar below GitHub's own. The looser set cannot admit a pull request that fails the real test; the stricter one can reject one that passes it.

**Text GitHub renders as code is stripped before matching, and the expectations come from GitHub's renderer.** Fenced blocks, indented blocks, code spans and HTML comments are removed, inside a blockquote as well, so a reference in any of them does not count. *Rejected: matching the raw body. Also rejected: stripping only fences and single-backtick spans,* which was the first implementation and left several ways to pass the gate while linking nothing. Partial stripping is worse than none, because it reports green for a body whose reference GitHub never linked. It also closes a trap specific to this repository: `CLAUDE.md`, the constitution and several command prompts quote `Closes #<N>` in backticks constantly, and a pull request template is mostly commented-out instructions, so a pull request whose body *documents* the convention would otherwise pass the gate it was describing.

*Rejected, and this is the decision that cost the most: deciding what counts as code by reasoning about CommonMark.* Two review rounds produced a dozen defects in exactly that reasoning, in both directions — bodies passed that GitHub renders as code, and correctly-linked bodies were refused. The rules are now pinned against output from GitHub's own Markdown API (`POST /markdown`, `mode=gfm`), queried per case, and the differences from a naive reading are not subtle once asked: an indented chunk cannot interrupt a paragraph, but it does open a code block at the start of the body and after a heading, a thematic break or a fence; inside a list, code starts four columns past the item's content column, so five spaces may be prose where six is code; only `1.` may interrupt a paragraph as an ordered marker; and a code span is a run of N backticks closed by a run of exactly N, which cannot span a blank line. A single-backtick matcher reads ```` ``Closes #1`` ```` as an empty span and leaves the reference exposed; a matcher with no blank-line limit pairs two unrelated backticks across paragraphs and deletes the keyword between them.

**A reference is resolved at the number GitHub would resolve, and reported at the number the author wrote.** Leading zeros are stripped; a run of digits too long to be an issue number, and zero itself, are rejected. *Rejected: normalising with `$((10#$NUM))`,* which wrapped silently on a long run of digits and named an issue the body never mentioned. *Also rejected: refusing leading zeros outright,* which was this branch's second attempt and was simply wrong — GitHub's renderer autolinks `#0401` and `#00401` to issue 401, so refusing them failed pull requests that really did close their issue. The digit guard is set where GitHub stops autolinking, which was measured rather than assumed.

**The issue's identity is checked by exact url, not by an `/issues/` substring.** *Rejected: testing the url for `*/issues/*`.* `gh issue view` answers 0 for two things that are not this repository's issue at this number: a pull request at that number, and an issue transferred to another repository, which still resolves here through GitHub's redirect and answers with its new home. A substring test passed the transferred case and printed the other repository's url in its own success line. Equality settles both, and it is the test `.claude/commands/raise-pr.md` already applied for the same reason.

**A failure to reach GitHub is reported in different words from a body with no link.** The check reads `gh`'s stderr rather than its exit code, because "could not resolve to an issue or pull request" and an auth failure both exit non-zero and are opposite answers. *Rejected: treating any lookup failure as "that reference does not link".* The two verdicts send the author to different places, and the wrong one sends them to fix a body that is already correct. This is the same fail-closed rule, and the same answer/outage seam, as `traceability-check.sh`.

**An unterminated code fence fails rather than passing as unlinked.** A fence left open hides every line below it, so the body cannot be read. *Rejected: scanning what is left.* Telling an author to add a keyword that is sitting below their broken fence is the one verdict guaranteed to be unhelpful; "an unreadable body is not an unlinked one" is the same judgement `traceability-check.sh` makes about an issue body.

**Cross-repository references are extracted in order to be rejected by name.** `owner/repo#N` and full issue URLs are parsed, then rejected unless the slug is this repository (compared case-insensitively, as GitHub treats slugs). *Rejected: matching only bare `#N` and ignoring the rest.* Ignoring them would report "no closing keyword" about a body that plainly has one, which reads as a bug in the gate rather than a verdict on the body.

**The two ruleset changes are post-merge steps, not part of this branch.** The workflow, the check and its matrix are committed; registering `issue-link` as a required status check and deleting the repository-admin bypass actor are left to be done in the repository settings after merge. *Rejected: mutating the live ruleset from the build.* Three reasons. A ruleset is not a repository artefact, so the change cannot be committed, reviewed on the pull request, or reverted with it. Requiring a context whose workflow is not yet on `main` blocks every pull request cut before this one, since no `issue-link` run is ever reported for them. And removing the admin bypass before this branch has merged would remove the escape hatch while the gate enforcing it is still unreviewed. The repository already works this way: registering a fixed-name context in `Main CI/CD` was the post-merge step on issue #319 too.

**Residuals:**

- **The job runs the pull request's own copy of the check.** `actions/checkout` on `pull_request` gives the merge ref, so `bash scripts/pr-issue-link-check.sh` executes the head-ref version — a pull request that inserted an early `exit 0`, or loosened the keyword or state test, would make `issue-link` report success having verified nothing. This is the same hazard class as the `paths:`/`if:` warning in the workflow, and it is **not** closed here: every script-based gate in this repository shares it, `traceability.yml` included, so closing it belongs in one change covering both rather than in this branch. The mitigation today is that the script is read in review. Candidate fixes, for whoever picks it up: run `git show origin/main:scripts/pr-issue-link-check.sh` instead of the checked-out copy, or put a CODEOWNERS entry on the script.
- **An issue the token cannot see may be indistinguishable from one that does not exist.** GitHub's GraphQL is documented to answer not-found rather than forbidden for objects a token may not read, and the check treats that wording as a definitive answer about the reference — so a token lacking `issues: read` would likely report "no issue at that number" about a genuinely open issue. This branch did **not** verify what a denied read actually emits; the workflow grants the scopes so the question does not arise, and the comment there says as much rather than asserting a behaviour nobody measured. If the scopes are ever narrowed, settle this first.
- **The gate re-implements someone else's Markdown parser, and that is the standing risk.** Deciding what GitHub renders as code is a parsing problem, and a shell gate will trail the real parser indefinitely: two review rounds found a dozen defects here, in both directions. The expectations are now pinned against GitHub's own renderer, which is why the current set agrees with it on 41 of 42 probed bodies, but the corpus is a sample and not a proof. The structural fix is to stop parsing: `closingIssuesReferences` on the pull request is GitHub's own answer to "what will merging close?", and it would delete the keyword regex, all four strippers, the slug comparison and the number handling at once. It is not adopted here because it also counts Development-sidebar links, which issue #332's confirmed decision excludes — so the choice is between much less code with no parser to outrun, and keeping that exclusion. That is a decision for the maintainer, not something to settle inside a verification pass, and it is the first thing to weigh if this check needs a third round of markdown fixes.
- **A sidebar-only link fails the gate.** This follows from the confirmed decision rather than from GitHub's behaviour, and it means an author who linked their issue through the Development sidebar and nowhere else is told to add a keyword. That is intended; the wording of the failure says so.
